# Database Guardian — Workflow

## Step-by-Step Workflow

1. **Receive schema change request** — Read the feature spec; understand what new data must be stored or changed
2. **Review existing schema** — Open `prisma/schema.prisma`; identify affected models and relationships
3. **Design the change** — Draft the new or modified model fields; choose correct Prisma field types and attributes
4. **Plan indexes** — Identify every field that will be used in filters, joins, or ordering; add `@@index` directives
5. **Handle cascade rules** — For new relationships, explicitly define `onDelete` and `onUpdate` behavior; document the reason
6. **Generate migration** — Run `npx prisma migrate dev --name <descriptive-name>`
7. **Review migration SQL** — Open the generated `migration.sql`; confirm it matches intent; look for unintended table drops
8. **Test on development** — Verify the migration applies cleanly; run seed data; confirm application queries work
9. **Run Prisma validate** — Execute `npx prisma validate` and `npx prisma generate`
10. **Test on staging** — Apply migration to staging database; run integration tests; check query performance
11. **Coordinate production migration** — Hand off to deployment-engineer with migration runbook
12. **Post-migration verification** — Confirm row counts are correct; spot-check critical queries; monitor error logs

---

## Decision Points

| Situation | Action |
|---|---|
| Adding a new nullable field | Safe — generate migration, apply directly after review |
| Adding a new required field to an existing table | Provide a `@default` value or migrate in two steps: add nullable → backfill → add constraint |
| Renaming a column | Never rename directly — add new column, migrate data, remove old in separate PRs |
| Dropping a table or column | Requires data archival plan; coordinate with backend-engineer to remove all references first |
| Adding a unique constraint to existing data | Check for existing duplicates first; handle conflicts before applying constraint |
| Query returns too slowly (>200ms) | Run `EXPLAIN ANALYZE`; add index; benchmark before and after |
| Prisma migrate deploy fails on production | Do NOT retry blindly — assess the state; restore from backup if data is corrupted |
| New model requires full-text search | Evaluate Postgres `tsvector` or external search service; document the decision |

## Handoff Instructions

**Handing off to backend-engineer:**
- Provide the updated TypeScript types generated by `prisma generate`
- Document any renamed fields or changed types that break existing queries
- Share the migration name and timestamp so the engineer can update references

**Handing off to deployment-engineer:**
- Provide the exact `npx prisma migrate deploy` command to run
- Specify whether a pre-migration backup is required
- Confirm staging migration was successful and provide evidence (row counts, test results)

**Handing off to auth-security-guardian:**
- Flag any schema changes that affect `User`, `Session`, `Account`, or `Role` models
- Describe how the change affects session data or role resolution

**Handing off to production-hardening-agent:**
- Flag any schema change that affects the health check query
- Report connection pool configuration if changed in `lib/db.ts`
