# Implementation Plan: NextShop E-Commerce Platform

**Branch**: `001-nextshop-ecommerce-platform` | **Date**: 2026-05-18
**Spec**: `specs/nextshop-ecommerce-platform/spec.md`
**Input**: Feature specification + user-provided architecture directives

---

## Summary

NextShop is a full-stack ecommerce platform built on Next.js App Router with
TypeScript, Tailwind CSS, Prisma/PostgreSQL, NextAuth, and Vercel deployment.
The implementation follows a stability-first, incremental delivery strategy:
foundation → catalog → auth → cart → checkout → orders → admin → hardening.
Each phase is independently testable and deployable. Payment processing uses
Stripe with webhook-confirmed order creation and idempotency keys to prevent
duplicate charges.

---

## Technical Context

**Language/Version**: TypeScript 5.x (strict mode — `"strict": true`)
**Framework**: Next.js 14+ App Router (React Server Components default)
**Styling**: Tailwind CSS 3.x with project design tokens in `tailwind.config.ts`
**ORM**: Prisma 5.x with PostgreSQL adapter
**Storage**: PostgreSQL 15+ (Vercel Postgres or managed PG instance)
**Auth**: NextAuth v5 (Credentials provider + JWT sessions)
**Payments**: Stripe (PaymentIntents API + webhook verification)
**Deployment**: Vercel (preview-first workflow; instant rollback enabled)
**Testing**: Manual acceptance testing per user story; CI via `lint + typecheck + build`
**Performance Goals**: LCP < 2.5s on mobile; TTFB < 500ms for product listing
**Constraints**: No experimental packages; all deps must be production-stable releases

### Phase 1 — Product Catalog (US1: P1)

**Goal**: Browsable, responsive product storefront — no auth required.

**Deliverables**:
- `app/(shop)/products/page.tsx` — ISR product listing (revalidate: 60)
- `app/(shop)/products/[id]/page.tsx` — dynamic product detail
- `app/not-found.tsx` updated for invalid product IDs
- `components/product/` — ProductCard, ProductGrid, ProductDetail, StockBadge
- `components/ui/` — Skeleton, Card, Badge
- `services/product.service.ts` — `getProducts()`, `getProductById()`

**Performance requirement**: Product listing page MUST use ISR (`revalidate: 60`).
LCP image MUST use `next/image` with `priority` prop.

**Checkpoint**: `/products` renders a grid of seeded products. `/products/[id]`
renders detail page. Invalid ID shows 404. Skeleton shows while loading.

### Phase 2 — Authentication (US2: P1)

**Goal**: Signup, login, session persistence, and protected route redirection.

**Deliverables**:
- `app/(auth)/login/page.tsx` + `app/(auth)/signup/page.tsx`
- `app/api/auth/[...nextauth]/route.ts`
- `features/auth/` — signup server action, login form component
- `middleware.ts` updated with route matchers for `/cart`, `/checkout`, `/orders`
- `components/layout/Navbar.tsx` — auth state in nav (sign in / sign out)

**Security requirement**: `NEXTAUTH_SECRET` and `NEXTAUTH_URL` must be verified in
Vercel before deployment. All session checks use `getServerSession()` — never
client-passed identity.

**Checkpoint**: New user can sign up → session established. Existing user can sign in
and out. Unauthenticated user hitting `/cart` redirected to `/login`.

---

### Phase 3 — Shopping Cart (US3: P2)

**Goal**: Cart persistence, item management, and correct total calculation.

**Deliverables**:
- `app/(shop)/cart/page.tsx`
- `app/api/cart/route.ts` — GET, POST (add), PUT (update qty), DELETE (remove)
- `services/cart.service.ts`
- `features/cart/` — cart server actions
- `components/cart/` — CartItem, CartSummary
- `hooks/useCart.ts` — optimistic cart state

**Data rule**: Cart is created lazily on first add-to-cart. `upsert` on CartItem
with `@@unique([cartId, productId])` prevents duplicates (FR-014).

**Checkpoint**: Authenticated user adds product → cart updates. Quantity updates
calculate correctly. Cart persists on page refresh.

---

### Phase 4 — Checkout & Payment (US4: P2)

**Goal**: Stripe payment flow with webhook-confirmed order creation and idempotency.

**Deliverables**:
- `app/(shop)/checkout/page.tsx` + `app/(shop)/checkout/success/page.tsx`
- `app/api/checkout/route.ts` — POST creates Stripe PaymentIntent
- `app/api/webhooks/stripe/route.ts` — handles `payment_intent.succeeded`
- `services/payment.service.ts` — PaymentIntent creation, idempotency key strategy
- `services/order.service.ts` — atomic order creation via `$transaction`
- `components/checkout/` — CheckoutForm, OrderSummary, PaymentForm

**Critical rules**:
- Price MUST be recalculated server-side from DB (FR-016)
- Order MUST only be created after webhook confirmation (FR-017)
- Idempotency key: `stripe-pi-${userId}-${cartId}` (FR-018)
- Stock decrement inside `$transaction` with `stock: { gte: qty }` guard (FR-019)
- Stripe webhook signature MUST be verified with `STRIPE_WEBHOOK_SECRET`

**Checkpoint**: Stripe test card `4242 4242 4242 4242` → order created, stock
decremented, success page shown. Declined card `4000 0000 0000 0002` → error shown,
no order in DB.

---

### Phase 5 — Order History (US5: P3)

**Goal**: Authenticated user views their own orders; no data leakage.

**Deliverables**:
- `app/(dashboard)/orders/page.tsx` — order list
- `app/(dashboard)/orders/[id]/page.tsx` — order detail
- `app/api/orders/route.ts` + `app/api/orders/[id]/route.ts`
- `services/order.service.ts` updated with user-scoped queries
- `components/order/` — OrderCard, OrderDetail, OrderStatusBadge

**Security rule**: All order queries MUST include `where: { userId: session.user.id }`
— never return orders for other users (FR-021).

**Checkpoint**: User with orders sees their order list. User with no orders sees empty
state. Unauthenticated user redirected to login.

---

### Phase 6 — Admin Dashboard (US6: P3)

**Goal**: ADMIN-role users can manage products and view all orders.

**Deliverables**:
- `app/admin/` pages: dashboard, products list, new product, edit product, orders
- `app/api/admin/products/route.ts` + `app/api/admin/orders/route.ts`
- `components/admin/` — ProductForm, AdminProductTable, AdminOrderTable
- `features/admin/` — admin server actions

**Security rule**: All `/admin` and `/api/admin` routes double-check
`session.user.role === "ADMIN"` server-side. Middleware is the first gate;
handler is the second (defence in depth).

**Product delete rule**: Products with existing OrderItems MUST NOT be deleted — soft
delete (set `active: false`) instead. This satisfies FR-026 without data corruption.

**Checkpoint**: Admin user creates product → appears in storefront. Admin edits price
→ storefront reflects new price within ISR revalidation interval. Customer role
attempting `/admin` receives 403.

---

### Phase 7 — Production Hardening

**Goal**: Error boundaries, security headers, rate limiting, monitoring.

**Deliverables**:
- `next.config.ts` security headers (X-Frame-Options, CSP, HSTS, etc.)
- `middleware.ts` — rate limiting on `/api/auth/` and `/api/checkout/`
- `app/error.tsx` refined with Sentry integration
- Sentry configured: `sentry.server.config.ts` + PII scrubbing
- `app/api/health/route.ts` — DB connectivity check verified in production

**Checkpoint**: Security headers visible in browser DevTools. Health check returns
`{ status: "ok", db: "connected" }`. Test error reaches Sentry.

## Key Architectural Decisions

### Decision 1: Webhook-First Order Creation
**Problem**: Stripe payment success can fire on the client redirect before the server
processes it, causing duplicate or missing orders.
**Decision**: Order is created ONLY inside the `payment_intent.succeeded` webhook
handler — never on the client success redirect.
**Trade-off**: Slight UX delay on order confirmation page (polls for order by
payment intent ID). Acceptable for correctness guarantee.

### Decision 2: Atomic Stock Decrement
**Problem**: Concurrent purchases of the last unit can oversell.
**Decision**: `$transaction` with `stock: { gte: quantity }` guard on `Product.update`.
If constraint fails, transaction rolls back and user receives out-of-stock error.
**Trade-off**: Slightly higher DB load per checkout. Acceptable — correctness is non-negotiable.

### Decision 3: ISR for Product Listing
**Problem**: Product listing can't use `cache: 'no-store'` (too slow) or SSG (too stale).
**Decision**: `revalidate: 60` ISR — pages rebuild every 60 seconds.
**Trade-off**: Price/stock changes take up to 60 seconds to reflect. Acceptable for
a product catalog; unacceptable for cart/orders (those use dynamic rendering).

### Decision 4: Soft Delete for Products
**Problem**: Hard-deleting a product with existing OrderItems would corrupt order history.
**Decision**: `product.active = false` instead of DELETE. Admin UI hides inactive products from storefront. Order items retain the product reference for order history display.
**Trade-off**: Products table grows over time. Acceptable at this scale.
